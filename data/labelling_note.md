# Data and labelling note

## Where the data came from

The **Employees** sample database from Kaggle — six linked tables covering
employees, departments, salaries, titles and management history.

| Table | Rows | What it holds |
|---|---:|---|
| `departments` | 9 | department code and name |
| `dept_manager` | 24 | who managed which department, and when |
| `dept_emp` | 331,603 | which employee belonged to which department, and when |
| `employees` | 300,024 | one row per person |
| `titles` | 443,308 | job title history |
| `salaries` | 967,330 | salary history |

Chosen because the tables genuinely join, so questions can require two or
three joins, date filtering and aggregation. A single flat table would have
let every model score near 100%, and the brief warns that then we learn
nothing.

### Rebuilding it

The CSVs (~92 MB) and the built database are both gitignored. The repo holds
the recipe, not the output:

```bash
# download the Employees dataset from Kaggle, unzip into data/raw/
python data/build_db.py
```

`build_db.py` drops the unnamed row-number column Kaggle ships, loads the six
tables, creates indexes, and then **asserts the row counts above**. If a CSV
were truncated or the wrong file, the build fails instead of quietly producing
a database our questions would be wrong about.

### Note on the date sentinel

This dataset uses `to_date = '9999-01-01'` to mean "still current" rather than
`NULL`. Several questions depend on it. Models that assume `NULL` get these
wrong, which is a legitimate difficulty, not a flaw in the question.

## The questions

60 items in `data/items.jsonl`, generated by `data/generate_items.py`.

```json
{"id": "q001", "question": "How many employees are in the database?",
 "gold_sql": "SELECT COUNT(*) AS employee_count FROM employees;",
 "difficulty": "easy", "split": "dev"}
```

| Split | Items | easy | medium | hard |
|---|---:|---:|---:|---:|
| dev (practice) | 10 | 5 | 3 | 2 |
| **test (graded)** | **50** | 10 | 22 | 18 |
| total | 60 | 15 | 25 | 20 |

The dev items exist so the harness can be tested without touching the 50 that
produce the reported numbers. `q041` and `q046` were moved into dev (and
`q009`, `q010` out of it) so that dev contains hard items — otherwise the first
three-join query with date arithmetic that any model saw would be during the
real run, and a parsing bug would surface at the worst possible moment.

Item IDs are stable and are not renumbered when an item changes split. `q041`
being a dev item is not a mistake.

- **easy** — one table, one filter or aggregate
- **medium** — a join plus `GROUP BY`, or an `ORDER BY … LIMIT`
- **hard** — two or more joins, a subquery or window function, date arithmetic,
  or the `9999-01-01` sentinel

## Problems found, and what was done

**`q051` — replaced.** The original asked "which departments have no current
manager?" and returned zero rows: all nine departments do have one, so the true
answer was "none". The SQL was correct but the item was weak — a model could
return an empty result from a completely wrong query and still be marked
correct. Replaced with *"Which departments have had more than two different
managers, and who is the current one?"* — same theme, same difficulty, returns
3 rows, and needs a self-join on `dept_manager` plus the date sentinel.

**`q060` — replaced.** The original asked which departments have more current
employees than all departments whose code starts with `d00`. All nine
department codes start with `d00`, so it asked a set to exceed its own maximum.
Logically impossible, always empty. Replaced with *"Which departments have an
average current salary above the company-wide average current salary?"* — same
compare-against-an-aggregate shape, returns 3 rows.

Both replacements were written and tested before any model was run. This is not
the same as dropping an item a model failed, which is forbidden.

**Slow gold queries — solved by caching.** Several gold queries scan the
967k-row salaries table and took 3–10 seconds. Indexes in `build_db.py` fixed
most; `q043` and `q045` are still multi-second by nature.

This mattered because a *gold* query exceeding the scorer's timeout would fail
the item regardless of what the model did. The fix is `src/cache_gold.py`: every
gold query runs once, with a 120-second timeout, and a hash of its normalised
result is stored in `data/gold_results.json`. Scoring then runs only the model's
query and compares hashes — one query per item instead of two, and gold timing
stops mattering.

```bash
python -m src.cache_gold     # re-run whenever items.jsonl changes
```

The normalisation rules live in `src/sqlutil.py` and are used by both the cache
and the scorer, so they cannot drift apart: column names ignored (aliases
differ legitimately), floats rounded to 6 places, `NULL` distinct from `0` and
from the string `"NULL"`, duplicate rows significant, and row order compared
only when the gold query has its own `ORDER BY`.

## Changes made when the data was brought into this repo

- CSVs moved from `archive/` to `data/raw/` (gitignored)
- `query_trials.db` renamed to `database.sqlite` so `*.sqlite` in `.gitignore`
  catches it — as `.db` it would have been committed, and at 83 MB that would
  have been rejected by GitHub
- `items.jsonl` gained `id`, `difficulty` and `split` fields. The difficulty
  labels already existed in `generate_items.py` but were dropped when the file
  was written; without `id` there is no stable way to join results back to
  questions in `per_item.csv`
- Indexes and row-count assertions added to `build_db.py`
- `data/schema.sql` added — this exact text is what goes into the prompt
